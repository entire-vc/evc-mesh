# Typed turn outcomes — data model and command API

Status: implementation contract. The schema (migration
`20261028001_typed_outcomes.sql`), the two reads and the commands `wait_for`,
`continue_next`, `hand_off` and `add_note` are implemented; `ask_agent`,
`answer_decision` and `finish_task` are planned. Routes, bodies, responses and
error codes are fixed here so the server handlers, the MCP tools and the runner
can be built in parallel against the same contract.

An agent's turn ends with a command, not with a marker line in a comment. The
command validates its input on the server, writes the state, writes a
human-readable comment generated by the server and, where the command says so,
releases the checkout, all in one transaction. A refusal writes nothing and
returns the reason in the same turn.

## Data model

| table / column | purpose |
|---|---|
| `task_waits` | the one active wait of an agent on a card |
| `turn_outcomes` | append-only journal of how each turn ended |
| `decision_requests` | a question one agent asks another |
| `tasks.result_kind` | what a closed card delivered |
| `comments.metadata.wakes` | `false` marks a note that wakes nobody |

### `task_waits`

| field | type | notes |
|---|---|---|
| `id` | uuid | |
| `task_id`, `agent_id` | uuid | the waiting card and agent |
| `session_id` | string ≤ 200, nullable | runner session that declared it |
| `kind` | `card` \| `mr` \| `pipeline` \| `time` \| `decision` \| `human` | |
| `target_task_id`, `target_condition` | uuid, dependency condition | `card`; condition defaults to `task_done` |
| `vcs_link_id`, `provider`, `project_path`, `mr_iid` | | `mr`; coordinates are stored even when a link is given |
| `project_path`, `pipeline_id`, `required_jobs[]` | | `pipeline` |
| `until` | string | `mr`: `merged` \| `green` \| `changed`; `pipeline`: `finished` \| `green` |
| `until_at` | timestamp | `time` |
| `decision_request_id` | uuid | `decision` |
| `human_gate_ref` | string ≤ 200 | `human` |
| `note` | string ≤ 500 | |
| `created_at`, `resolved_at` | timestamp | |
| `resolution` | `met` \| `superseded` \| `cancelled` \| `expired` \| `invalid` | set together with `resolved_at` |

One active wait per `(task_id, agent_id)`, enforced by the partial unique index
`task_waits_one_active`. A new wait resolves the previous one as `superseded`
in the same transaction.

### `turn_outcomes`

`id, task_id, agent_id, session_id?, turn_id?, kind, wait_id?, result_kind?, note (≤ 4096), created_at`.
`kind` is `next` \| `wait` \| `done` \| `review` \| `handoff` \| `cancelled`;
`wait_id` is set exactly when `kind = wait`. Rows are never updated (a trigger
refuses `UPDATE`) and leave only with their task.

The runner reads the newest outcome of its session. No outcome after a turn is
the explicit `no_outcome` state, not a parse failure.

### `decision_requests`

`id, task_id, from_agent_id, to_agent_id, question (≤ 4000), state, answer_comment_id?, answered_at?, created_at`.
`state` is `open` \| `answered` \| `withdrawn`. The addressee is an agent id from
the team directory, never an @-handle; asking yourself is refused. The same
open question (compared trimmed and case-insensitively) from the same agent to
the same addressee on the same card is one request: asking again returns it.

### `tasks.result_kind`

`change` \| `defect` \| `research` \| `content` \| `ops`, nullable, set when a card
is closed by `finish_task`. The matching `kind:*` label is kept in sync for
dashboards and reports.

### `comments.metadata.wakes`

Boolean, default `true`. `false` marks a note: no mention or handoff delivery is
created and no waiting runner is woken. Absent, `null` or a non-boolean value
reads as `true` (`domain.CommentWakes`).

## Reads

Both require workspace membership, like every `/tasks/:task_id/...` read.
`:task_id` is a full UUID or a 6–12 hex short id.

### `GET /api/v1/tasks/:task_id/turn-outcomes`

Query: `session_id` (optional — one session's outcomes), `limit` (1–100, default 20).

`200` — array of `turn_outcomes` rows, newest first. `[]` when there are none.

### `GET /api/v1/tasks/:task_id/wait`

Query: `agent_id` (optional — that agent's wait; without it, the newest active
wait on the card).

`200` — the active `task_waits` row. `404` with `error_code: no_active_wait`
when there is none (a missing card is `404 not_found`).

## Commands

Common to all commands:

- Caller: an authenticated agent (agent API key). A user key gets `403 forbidden`
  except on `answer_decision` and `add_note`, which people may also use.
- Optional body fields on every task command: `session_id` and `turn_id` (strings
  ≤ 200), copied onto the outcome and the wait.
- The generated comment is returned as `comment_id`; its body is written by the
  server from the command, so agents no longer compose marker lines.
- Response envelope on success:

  ```json
  {
    "outcome": { "...": "turn_outcomes row, absent for answer_decision and add_note" },
    "wait": { "...": "task_waits row, when the command declared one" },
    "comment_id": "uuid",
    "task": { "id": "uuid", "status": "slug", "assignee_id": "uuid|null" },
    "released": true
  }
  ```

- Error envelope: the standard API error
  `{"code": <http status>, "error_code": "<code>", "message": "...", "details": "..."}`.
  The codes specific to these commands are all `422`:

  | `error_code` | meaning |
  |---|---|
  | `invalid_target` | the target does not exist, is not reachable from this card, or its fields are incomplete for the kind |
  | `self_wait` | a card waits on itself |
  | `already_met` | the target is already in the awaited (or another terminal) state: an MR merged or closed, a pipeline finished, a card closed |
  | `time_out_of_bounds` | `until_at` is less than 5 minutes or more than 30 days away |
  | `not_an_agent` | the addressee of `ask_agent` or `hand_off` is not an agent of the directory |
  | `missing_result_kind` | `finish_task` without a valid `result_kind` |
  | `missing_evidence` | `finish_task` without evidence |

  Generic codes keep their meaning: `400 bad_request` (malformed body),
  `403 forbidden`, `404 not_found` (card or request), `409 conflict` (the caller
  does not hold the card's checkout, or the request is no longer open).

### 1. `wait_for` — `POST /api/v1/tasks/:task_id/wait`

```json
{
  "on": "card | mr | pipeline | time",
  "target_task_id": "uuid",            "target_condition": "task_done | shipped | deployed | accepted | ...",
  "vcs_link_id": "uuid",               "provider": "gitlab", "project_path": "group/project", "mr_iid": 12,
  "pipeline_id": 7001,                 "required_jobs": ["test"],
  "until": "merged | green | changed | finished",
  "until_at": "2026-10-29T06:00:00Z",
  "note": "≤ 500 chars"
}
```

Only the fields of the chosen `on` are read. For `mr`, either `vcs_link_id` (a
link of this card) or `provider` + `project_path` + `mr_iid` (a link of this card
or an MR of the project) names the target. For `card` a `blocks` dependency with
`target_condition` is created or reused. Writes the wait (superseding the
caller's previous one), an outcome `wait`, the comment, and releases the checkout.

`201` — envelope with `outcome`, `wait`, `released: true`.
Errors: `invalid_target`, `self_wait`, `already_met`, `time_out_of_bounds`.

How the target is confirmed:

- `card` — the card exists in the same workspace and the edge's condition is
  not already released (a closed card for `task_done`); a cycle in the
  dependency graph is `invalid_target`. The `blocks` edge is written in the
  same transaction.
- `mr` — live from the workspace's GitLab when it is configured, otherwise from
  a pr link of this card. Not found on either is `invalid_target`; merged or
  closed is `already_met`. A matching link of the card is recorded on the wait.
- `pipeline` — live from the workspace's GitLab only; without it the target
  cannot be confirmed and is `invalid_target`. `success`, `failed`, `canceled`
  and `skipped` are `already_met`.

The card's `runtime_state` becomes `waiting` with `ref = "wait:<wait id>"` and,
for `time`, `until = until_at`. Such a state is not refreshed by the runner, so
it reads stale only after its `until`, not after the usual 15 minutes.
A timer cannot ask anyone to act: a wait on another agent is `ask_agent`, on a
person `ask_human` (the existing `set_human_gate`, which records a `human` wait).

### 2. `continue_next` — `POST /api/v1/tasks/:task_id/next`

```json
{ "note": "what was done, ≤ 4096 chars" }
```

Writes an outcome `next` and the comment; the card stays with the caller and the
checkout is extended. `200` — envelope with `outcome`, `released: false`.
Errors: `409 conflict` when the caller does not hold the checkout.

### 3. `ask_agent` — `POST /api/v1/tasks/:task_id/decision-requests`

```json
{ "to": "agent name or uuid from the team directory", "question": "≤ 4000 chars" }
```

Opens a decision request (or returns the open identical one), declares a
`decision` wait on it, writes an outcome `wait` and the comment, and releases the
checkout. `201` — envelope with `outcome`, `wait`, `released: true`, plus
`decision_request` and `reused: true|false`.
Errors: `not_an_agent` (unknown name, a person, or the caller itself).

### 4. `answer_decision` — `POST /api/v1/decision-requests/:request_id/answer`

```json
{ "answer": "≤ 4000 chars" }
```

Only the addressee (or a person) may answer. Writes the answer as a comment on
the asking card, marks the request `answered` with `answer_comment_id`, and
resolves the asker's `decision` wait as `met`, which wakes the asker. A comment
by the addressee with `metadata.answers = <request_id>` has the same effect.
`200` — `{ "decision_request": {...}, "comment_id": "uuid" }`.
Errors: `403 forbidden` (not the addressee), `404 not_found`,
`409 conflict` (request answered or withdrawn).

### 5. `finish_task` — `POST /api/v1/tasks/:task_id/finish`

```json
{
  "result_kind": "change | defect | research | content | ops",
  "evidence": "text ≤ 4096 chars",
  "evidence_links": ["https://..."],
  "to": "done | review"
}
```

Sets `tasks.result_kind` and the matching `kind:*` label, moves the card to its
`done` or `review` status, writes an outcome `done` or `review` with the result
kind, writes the evidence as the closing comment, resolves the caller's active
wait as `cancelled`, and releases the checkout. Existing move gates (closing
comment length, done-evidence on linked MRs, open subtasks) still apply and
return their own errors. `200` — envelope with `outcome`, `released: true`.
Errors: `missing_result_kind`, `missing_evidence`.

### 6. `hand_off` — `POST /api/v1/tasks/:task_id/handoff`

```json
{ "to": "agent name or uuid from the team directory", "why": "≤ 4000 chars" }
```

Assigns the card to the addressee, moves it to its first `todo` status, writes an
outcome `handoff` and the comment, resolves the caller's active wait as
`cancelled`, and releases the checkout — one transaction instead of three calls
that race. `200` — envelope with `outcome`, `released: true`.
Errors: `not_an_agent`; `409 conflict` when a person pinned the assignee
(`assigned_by = human`). The addressee passes the same checks as `assign_task`
(workspace tenancy, accepts assignments) and is enrolled in the project.

### 7. `add_note` — `POST /api/v1/tasks/:task_id/notes`

```json
{ "text": "markdown" }
```

Writes a comment with `metadata.wakes = false`: no delivery, no wake, no outcome,
the checkout is untouched. `201` — `{ "comment_id": "uuid" }`.

## Compatibility

`move_task`, `add_comment` and `release_task` stay for people and integrations.
Fleet rules teach only the commands above.
